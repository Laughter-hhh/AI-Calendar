# AI Calendar v4.5.1 发布测试流

本流程把“能构建”提升为“功能、安全、布局与上线后健康状态全部通过”才允许部署。

## 1. 本地隔离验证

测试服务必须设置独立的 `DATABASE_PATH`，禁止连接生产数据库。

1. **静态门禁**：ESLint 零错误、TypeScript/Next.js 生产构建通过。
2. **核心算法**：时间线覆盖双重叠、三重叠、首尾相接、链式重叠和深夜边界。
3. **导入安全**：
   - 未登录拒绝导入；
   - 仅接受 UTF-8 `.ics`，拒绝 CSV/XLSX/JSON 和伪 ICS；
   - 预览阶段不写数据库；
   - 确认后只追加，原有日程不变；
   - 重复导入幂等；
   - 覆盖 UTC、TZID、全天事件、折行、复杂重复规则告警；
   - 起止时间可编辑，非法格式和结束早于开始均拒绝。
4. **渲染回归**：日/周/月、搜索、笔记、共享、帮助、下载页均返回正确内容；周视图三重叠并排，凌晨任务不被裁切。
5. **离线与布局契约**：Service Worker 只缓存静态资源，不缓存用户专属 API；离线回退页可访问；单日时间线 06:00 顶部保留 12px 留白。
6. **全量冒烟**：认证、自然语言解析、重复日程、增删改查、导出、共享、语音降级等原功能全部通过。

## 2. GitHub Actions 云端门禁

推送 `main` 后，云端依次执行：

1. 冻结锁文件安装依赖；
2. ESLint；
3. production build；
4. 使用临时 SQLite 启动 production server；
5. 执行解析、时间线、离线、冒烟、页面渲染、日历增强六套测试；
6. 只有全部成功才打包并上传服务器。

此阶段完全绕过个人电脑，电脑离线不会中断构建或部署。

## 3. 部署与回滚

服务器部署时先把当前应用保留为 `app.previous`，再启动新版本并循环检查 `/api/health`。

- 健康检查成功：删除旧应用目录，发布完成。
- 解压、启动或健康检查失败：自动恢复上一版本并重启 PM2，Action 标记失败。
- 数据库位于 `/opt/ai-calendar/database/data/ai-calendar.db`，不随应用目录替换。

## 4. 上线后验收

GitHub Action 成功后再次从公网请求：

- `/api/health` 返回 `ok: true`、`db: ok`；
- `/api/version` 返回 `4.5.1`；
- 首页可访问且包含事项/时间线切换。

三项都通过才视为本次上线完成。
